# Deep Code Review: QPG Backend API, Authentication, and Tenancy

## 1. Executive Summary

This document presents a deep code review of the Question Paper Generator (QPG) backend codebase, specifically focusing on `backend/config`, `backend/accounts`, API boundaries, serializers, views, URLs across backend packages, authentication/permissions, error handling, request validation, and migrations. 

### Key Findings
1. **Critical Tenancy Leakage**: The core `QuestionPicker` algorithm completely ignores user tenancy, permitting a school to fetch and include private questions uploaded or generated by other schools.
2. **Weak Authentication Controls**: Django's custom password validation is bypassed in registration. Authentication relies on non-expiring DRF tokens, and there is no logout endpoint.
3. **Data Inconsistencies & Logic Gaps**: Relational mappings (such as `PaperQuestion` rows) become stale and out-of-sync with the document JSON upon draft modification. Assembly errors leave broken database records.

## 2. Critical Findings

### C1: Cross-Tenant Data Leakage in Question Selection
* **File**: [picker.py](file:///Users/varad/V/repo/qs-paper-generator/backend/papers/picker.py#L157-L179)
* **Evidence**:
  In `QuestionPicker._fetch_candidates(opts)`, candidate questions are fetched using slot parameters but without filtering by the school associated with the requesting user:
  ```python
  @staticmethod
  def _fetch_candidates(opts: PaperOptions) -> QuestionPool:
      """Issue one ORM query per (section, qtype, marks) bucket."""
      buckets: set[_BucketKey] = {
          (s.bank_section, s.qtype, s.marks, s.subject_area)
          for s in opts.template.slots
      }
      pool: QuestionPool = {}
      for key in buckets:
          section, qtype, marks, subject_area = key
          qs = Question.objects.filter(
              section=section,
              qtype=qtype,
              marks=marks,
              parse_quality__in=["clean", "partial"],
          )
          # ...
  ```
  Since `Question.objects.filter` lacks tenancy checks, this query exposes private school-owned questions (where `school` is not null) to any other school.
* **Concrete Fix**:
  Pass the user's school context into `PaperOptions` (or retrieve it from `opts.requesting_user`) and apply a multi-tenancy filter `Q(school__isnull=True) | Q(school=school)` to the candidate queries:
  ```python
  @staticmethod
  def _fetch_candidates(opts: PaperOptions) -> QuestionPool:
      school = getattr(opts.requesting_user, "school", None) if opts.requesting_user else None
      buckets = {
          (s.bank_section, s.qtype, s.marks, s.subject_area)
          for s in opts.template.slots
      }
      pool = {}
      for key in buckets:
          section, qtype, marks, subject_area = key
          qs = Question.objects.filter(
              section=section,
              qtype=qtype,
              marks=marks,
              parse_quality__in=["clean", "partial"],
          )
          if school:
              qs = qs.filter(models.Q(school__isnull=True) | models.Q(school=school))
          else:
              qs = qs.filter(school__isnull=True)
          # ...
  ```

## 3. High Findings

### H1: Bypassing Django Password Validation on User Registration
* **File**: [serializers.py](file:///Users/varad/V/repo/qs-paper-generator/backend/accounts/serializers.py#L14-L31)
* **Evidence**:
  `RegisterSerializer` validates input fields using simple serializers but fails to run standard Django password validators. Setting `min_length=6` directly on the CharField does not invoke Django's custom `MinimumLengthValidator` configured in `settings.py`:
  ```python
  class RegisterSerializer(serializers.Serializer):
      email = serializers.EmailField()
      password = serializers.CharField(write_only=True, min_length=6)

      # ...

      def create(self, validated_data):
          return User.objects.create_user(
              email=validated_data["email"], password=validated_data["password"]
          )
  ```
  Consequently, common or simple passwords (e.g., "password", "123456") are accepted, completely bypassing the validation suite defined in `AUTH_PASSWORD_VALIDATORS`.
* **Concrete Fix**:
  Import `validate_password` and run it during serializer validation:
  ```python
  from django.contrib.auth.password_validation import validate_password

  class RegisterSerializer(serializers.Serializer):
      # ...
      def validate(self, attrs):
          # ...
          validate_password(attrs["password"])
          return attrs
  ```

### H2: Lack of Token Invalidation (Missing Logout Endpoint & Non-Expiring Tokens)
* **Files**: 
  - [views.py](file:///Users/varad/V/repo/qs-paper-generator/backend/accounts/views.py#L18-L43)
  - [urls.py](file:///Users/varad/V/repo/qs-paper-generator/backend/accounts/urls.py#L7-L11)
* **Evidence**:
  The system utilizes Django Rest Framework's default `TokenAuthentication`. Tokens are fetched/created via `Token.objects.get_or_create` and persisted indefinitely in `localStorage`. 
  There is no logout view defined in URL patterns, and tokens have no expiration policy. A teacher cannot revoke or invalidate their session from the server.
* **Concrete Fix**:
  1. Add a logout API view to delete the requesting user's token upon a POST request:
     ```python
     from rest_framework.views import APIView
     from rest_framework.response import Response
     from rest_framework import status
     from rest_framework.permissions import IsAuthenticated

     class LogoutView(APIView):
         permission_classes = [IsAuthenticated]

         def post(self, request):
             request.user.auth_token.delete()
             return Response(status=status.HTTP_204_NO_CONTENT)
     ```
  2. Implement a custom Token authentication class that checks the token creation timestamp and enforces an expiration window (e.g., 7 days).

## 4. Medium Findings

### M1: Out-of-Sync Relational Mapping (`PaperQuestion` Stale Links)
* **File**: [models.py](file:///Users/varad/V/repo/qs-paper-generator/backend/papers/models.py#L68-L85)
* **Evidence**:
  The database schema contains a relational mapping table `PaperQuestion` (`self.items`) connecting papers to questions. However, after assembly, subsequent edits and question swaps (made via `PaperEditorDraftView.patch`) only update the JSON `document` field on the `Paper` row; they never update the `PaperQuestion` rows.
  The docstring for `Paper.approve()` claims that it:
  > "...locks it (status → approved) and reconciles PaperQuestion rows from the final document."
  
  But the actual code lacks any relational reconciliation logic:
  ```python
  @transaction.atomic
  def approve(self) -> None:
      self.status = PaperStatus.APPROVED
      self.save(update_fields=["status"])
      qids = self._referenced_question_ids()
      if qids:
          Question.objects.filter(pk__in=qids).update(verified=True)
          self._record_usage(qids)
  ```
  Consequently, `PaperQuestion` records become stale and point to incorrect questions, rendering relational queries, joins, and reporting tools inaccurate.
* **Concrete Fix**:
  Implement the documented reconciliation inside `approve()`. Clear existing questions and repopulate them from the approved JSON document:
  ```python
  @transaction.atomic
  def approve(self) -> None:
      self.status = PaperStatus.APPROVED
      self.save(update_fields=["status"])
      qids = self._referenced_question_ids()
      if qids:
          Question.objects.filter(pk__in=qids).update(verified=True)
          self._record_usage(qids)
          
          # Reconcile relational mappings
          self.items.all().delete()
          document = self.document
          if isinstance(document, dict):
              rows = []
              order = 1
              for section in document.get("paper", {}).get("sections", []):
                  for slot in section.get("slots", []):
                      pk = _pk_from_question_id(slot.get("selectedQuestionId"))
                      if pk is not None:
                          rows.append(
                              PaperQuestion(
                                  paper=self,
                                  question_id=pk,
                                  order=order,
                                  section=section.get("id"),
                                  or_group=slot.get("orGroup"),
                              )
                          )
                          order += 1
              if rows:
                  PaperQuestion.objects.bulk_create(rows)
  ```

### M2: Orphaned and Malformed Database Records on Assembly Contract Validation Failure
* **File**: [builder.py](file:///Users/varad/V/repo/qs-paper-generator/backend/papers/builder.py#L43-L83)
* **Evidence**:
  `PaperBuilder.assemble()` handles paper creation and relational link insertion inside an atomic transaction: `self._persist(user, title, result)`. However, the final document build and `_guard_contract` validation are done outside of this transaction:
  ```python
  def assemble(self, user, ...) -> AssemblyResult:
      # ...
      result = QuestionPicker().select(opts)
      paper = self._persist(user, title, result) # atomic
      document = PaperDocumentBuilder().build(paper, result, opts, paper_format)
      self._guard_contract(paper, document) # Can raise PaperDocumentContractError
      paper.document = document
      paper.answer_document = build_answer_document(paper)
      paper.save(update_fields=["document", "answer_document"])
      return AssemblyResult(paper=paper, document=document)
  ```
  If `_guard_contract` detects a contract violation and throws a `PaperDocumentContractError`, the `_persist` transaction is already committed. The API view returns a 500 error, but a broken `Paper` record with `document = NULL` and `answer_document = NULL` is permanently left in the database.
* **Concrete Fix**:
  Decorate `PaperBuilder.assemble` with `@transaction.atomic` to ensure that any validation or contract failure rolls back the entire assembly, including the persisted paper and question links.

### M3: Insecure Persistent Token Transmission in URL Query Parameters
* **File**: [views.py](file:///Users/varad/V/repo/qs-paper-generator/backend/papers/views.py#L418-L423)
* **Evidence**:
  To render PDFs, the backend generates a browser URL containing the user's permanent authentication token in the query string:
  ```python
  def _frontend_print_url(user, paper_pk: int, route_suffix: str) -> str | None:
      base_url = settings.PAPER_PRINT_BASE_URL.rstrip("/")
      if not base_url:
          return None
      token, _ = Token.objects.get_or_create(user=user)
      return f"{base_url}/editor/{paper_pk}/{route_suffix}?token={token.key}"
  ```
  This persistent token is exposed in server logs (web server access logs), browser histories, and local browser memory.
* **Concrete Fix**:
  Generate short-lived, single-use access codes/tokens specifically for Playwright PDF rendering, or leverage secure HTTP-only cookies if the browser runs in the same origin.

### M4: Vulnerability to Distributed Brute-Force Attacks on Authentication
* **File**: [settings.py](file:///Users/varad/V/repo/qs-paper-generator/backend/config/settings.py#L122-L142)
* **Evidence**:
  The system implements IP-based rate limiting on authentication views (`RegisterView` and `LoginView`) via DRF's `ScopedRateThrottle` set to `5/min` for the `auth` scope. While this limits single-IP request rates, it does not prevent brute-forcing a specific email address by rotating a pool of client IPs. There is no account lockout logic or per-email throttling.
* **Concrete Fix**:
  Implement user account lockout (e.g., using `django-axes` or a custom throttle class that throttles attempts on a per-username/per-email basis).

### M5: Parsing Failures Crash Intent Classification View
* **File**: [assistant.py](file:///Users/varad/V/repo/qs-paper-generator/backend/ai_editor/assistant.py#L62-L82)
* **Evidence**:
  `classify_intent` runs `(make_model(...) | parser).invoke(prompt)` where `parser` is a `PydanticOutputParser` enforcing `IntentResult`. If the LLM generates slightly malformed JSON or invalid structures, the parser will raise an unhandled exception (e.g. `OutputParserException`), resulting in an unhandled HTTP 500 status code returned to the client:
  ```python
  result: IntentResult = (make_model(ModelPurpose.EDITOR_ASSISTANT) | parser).invoke(
      prompt
  )
  ```
* **Concrete Fix**:
  Add exception handling around the parser invocation. In the event of a parsing exception, return a safe fallback option (e.g., `off_topic` or standard `chat`):
  ```python
  from langchain_core.exceptions import OutputParserException
  import logging

  logger = logging.getLogger(__name__)

  try:
      result: IntentResult = (make_model(ModelPurpose.EDITOR_ASSISTANT) | parser).invoke(prompt)
      route = result.route if result.route in INTENT_ROUTES else "off_topic"
      reason = result.reason
  except OutputParserException as exc:
      logger.warning("LLM intent parsing failed, falling back to off_topic.", exc_info=True)
      route = "off_topic"
      reason = "Fallback classification due to parsing error."
  return {"route": route, "reason": reason}
  ```

## 5. Positive Notes

1. **AI Cost Protection**: The use of `base_revision` matching against `paper.revision` prior to launching long-running async AI jobs ensures the system cancels stale tasks before incurring paid LLM costs.
2. **Atomicity & Locking**: Critical view actions use `select_for_update` row locks (such as in claiming ingestion and generation batches), which successfully prevents database race conditions.
3. **Data Sanitization**: Question serializers cleanly omit the `answer` field to prevent accidental credential/answer key leakage to client views.

## 6. Suggested Tests

### Test 1: Cross-Tenant Picker Isolation
Verify that the `QuestionPicker` does not pull private tenant questions into another school's papers.
```python
def test_picker_does_not_leak_cross_tenant_questions():
    school_a = School.objects.create(name="School A")
    school_b = School.objects.create(name="School B")
    user_a = User.objects.create_user(email="teacher@schoola.com", school=school_a)
    
    # Private question belonging to School B
    chapter = Chapter.objects.create(slug="science-ch1", name="Chapter 1", order=1)
    Question.objects.create(
        school=school_b,
        chapter=chapter,
        section="A",
        qtype="mcq",
        marks=1,
        text="Private Question from School B",
        parse_quality="clean"
    )
    
    # Attempt to pick questions for School A
    opts = PaperOptions(
        template=TemplateBuilder().build("board"),
        chapter_slugs=["science-ch1"],
        requesting_user=user_a
    )
    pool = QuestionPicker()._fetch_candidates(opts)
    
    # The pool should be empty since School B's question is isolated
    bucket_key = ("A", "mcq", 1, None)
    assert bucket_key not in pool or len(pool[bucket_key]) == 0
```
